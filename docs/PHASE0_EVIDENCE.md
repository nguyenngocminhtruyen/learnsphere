## Java launcher regression follow-up (2026-10-27)

The default host Java 25 caused Gradle 8.14.3 build-script evaluation to fail with `Unsupported class file major version 69`. The existing compiler toolchain declaration did not select Gradle's own JVM. The repository now includes native daemon JVM criteria for Temurin JDK 21, portable provisioning URLs generated by `updateDaemonJvm`, and the Foojay settings resolver. Generated wrapper scripts and the Java 21 application toolchain are unchanged. CI includes a Java 25 launcher regression build after the primary Java 21 verification.

Executed in `apps/api` with the host's default Java 25 and only a writable Gradle cache override:

```sh
GRADLE_USER_HOME=/tmp/phase0-gradle-cache ./gradlew --version
GRADLE_USER_HOME=/tmp/phase0-gradle-cache ./gradlew clean test bootJar
GRADLE_USER_HOME=/tmp/phase0-gradle-cache ./gradlew --no-daemon \
  -Dorg.gradle.java.installations.auto-detect=false clean test bootJar --info
```

Both builds passed with all 3 Java tests and no failures/errors. The version output identified launcher Java 25 and daemon Java 21 criteria. Disabling installation detection forced first-run provisioning: the log records the Temurin 21.0.13 download, a new daemon started from Gradle's JDK cache and compilation with that JDK. No explicit `JAVA_HOME` or machine-specific JDK path was supplied. Raw provisioning evidence is in `/tmp/phase0-java25-regression.log`.

Also reran `python scripts/check_contracts.py` (validation and breaking-change self-test passed), `pytest apps/ai-service/tests` (3 passed, existing upstream httpx deprecation warning) and `docker compose build api` (Java 21 container build passed). CI workflow YAML parsed successfully. Hosted CI and Windows/macOS provisioning have not been executed. Initial JDK provisioning requires internet; Gradle 8.14.3 labels daemon discovery incubating.

Follow-up changed files: `apps/api/settings.gradle`, `apps/api/gradle/gradle-daemon-jvm.properties`, `.github/workflows/ci.yml`, `docs/PHASE0_OPERATIONS.md`, and this evidence document. This remains Phase 0 build configuration work.

## Failures encountered and resolved

- Sandbox DNS/cache/Docker socket restrictions blocked initial dependency downloads and checks; authorized escalated retries passed.
- Host default Java was 25, and installed Java 21 was a JRE without javac. Verification used a downloaded complete Java 21 JDK; Docker and CI use JDK 21.
- Initial MVC test configuration omitted the application security configuration; explicitly importing it made contract/security tests exercise the intended filter chain.
- CDK initially assumed egress subnets; explicit isolated subnet selection fixed synth.
- Host port 8080 was occupied by another service; configurable alternate ports resolved boot without disturbing that service.
- Initial dependency audit found advisories. Next.js/eslint-config-next were updated to 15.5.28; PostCSS 8.5.31 and Sharp 0.35.5 are pinned via workspace overrides. Final production audit reports 0 vulnerabilities. Full verification and Docker web build were rerun afterward.

## Remaining checks and risks

No hosted GitHub Actions run, PR/commit, AWS deployment, actual account/region/cost approval, production pgvector compatibility test, visual/browser accessibility check or production load test was performed. FastAPI's test client emitted one upstream httpx deprecation warning; tests passed. CDK reports default minHealthyPercent/feature-flag notices; services have zero desired tasks. Production deployment wiring, egress/ingress, task permissions and signed service identity are intentionally incomplete skeleton work. Python dependencies use version ranges, so future fresh installs may resolve newer versions; CI is the repeatability gate. The initial dependency/image downloads require internet access; local runtime requires no real AWS credentials.
